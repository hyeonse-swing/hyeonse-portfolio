## 여러 운영 도구에 나뉜 운행 업무

2024년 11월부터 2025년 8월까지 Yellow Bus 스쿼드의 프론트엔드 엔지니어로 일했어요. 인수한 통학 셔틀 서비스의 학생·배차·노선 업무는 PHP·JavaScript·React 기반의 여러 운영 도구에 나뉘어 있었습니다. 내부 운영팀과 학원은 쓰는 기능과 권한도 달랐어요. 저는 인수 초기 기술부채와 이전 방안을 함께 검토하고, 기존 기능을 React·TypeScript Admin의 운행 흐름으로 옮겼습니다.

로그인과 기본 UI를 먼저 준비했지만 운영 API가 모두 갖춰진 상태는 아니었어요. 기능별로 필요한 엔드포인트와 데이터 형태를 정리해 백엔드에 요청하고, 준비된 API부터 화면에 연결하는 방식을 제안했습니다. 기존 운영 화면을 참고해 학생 목록의 응답 형태도 맞췄어요. 보호자 정보가 없는 학생과 보호자가 여러 명인 학생을 예외로 다뤄야 했고, 백엔드가 공유한 변경 응답안에 맞춰 목록 화면을 이어갔습니다.

## 조건 선택이 지도와 목록에 함께 반영되도록

학원 담당자는 날짜별 배차, 여러 노선, 학생의 탑승 상태와 승하차 정류장을 확인하고 변경해야 했어요. 새 운행 화면에는 학원별 배차 조회, 복수 노선 지도, 탑승 상태와 정류장 변경, 접근 제한을 연결했습니다. 관제 데이터는 폴링으로 갱신하고 노선·정류장 관리에는 Kakao Map을 사용했어요. 관련 운행 화면 변경은 병합됐고, 이후 학생 탑승 일정과 위치의 일괄 등록 기능도 이어졌습니다.

화면에서는 학원·날짜·시간·배차 선택이 서로 어긋나지 않는 게 중요했어요. 선택 상태를 관리하면서 학원이 바뀌면 이전 선택을 초기화하고, 날짜가 바뀌면 시간과 경로 선택을 비웠습니다. 탑승 상태나 정류장 변경이 성공하면 관련 배차 상세·학생 일정·정류장 목록의 조회 캐시를 무효화해 서버 결과를 다시 보도록 했어요. 정류장을 드래그해 옮길 때는 같은 정류장인지, 노선 방향과 출발·도착 제약을 지키는지, 승하차 순서가 뒤집히지 않는지를 확인한 뒤 변경 확인으로 이어갔습니다.

## 재구성의 범위

운영자가 정류장 이름을 정확히 모를 때를 위해 주소 검색이나 학원에 연결된 정류장 후보에서 고르는 방안도 제안했어요. 이는 제안으로 기록된 내용이며, 모든 검색 방식의 운영 적용을 뜻하지는 않습니다. 학생 목록의 예외 데이터는 백엔드와 응답 계약을 조율했고, 운행 화면에는 접근 범위를 포함했습니다.

결과는 분산된 기능을 새 Admin의 운행 순서에 맞춰 재구성하고 초기 안정화에 참여한 경험이에요. 전체 레거시 이관의 완료 시점이나 안정화 효과를 보여 주는 정량 수치는 제시하지 않습니다. 더 자세한 화면·조회 흐름은 [Yellow Bus 사례](/work/yellow-bus/)에서 볼 수 있어요.
