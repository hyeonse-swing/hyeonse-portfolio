## 여러 도구에 흩어져 있던 운행 화면

Yellow Bus의 학생·배차·노선 업무는 PHP·JavaScript·React로 만든 여러 운영 도구에 나뉘어 있었어요. 내부 운영팀과 학원이 쓰는 기능과 권한도 달랐습니다. 저는 2024년 11월부터 2025년 8월까지 스쿼드의 프론트엔드 엔지니어로 일하며, 인수 초기 기술부채와 이전 방안을 검토하고 기존 기능을 React·TypeScript Admin의 운행 흐름으로 옮겼어요.

로그인과 기본 UI부터 준비했지만 운영 API가 한꺼번에 갖춰지지는 않았어요. 기능별 엔드포인트와 데이터 형태를 정리해 백엔드에 요청하고, 준비된 API부터 화면에 연결하는 방식을 제안했습니다. 학생 목록은 기존 운영 화면의 데이터를 대조하면서 응답 형태를 맞췄어요. 보호자 정보가 없거나 보호자가 여러 명인 학생도 있어서, 백엔드가 공유한 변경 응답안에 맞춰 목록의 예외 상태를 다뤘습니다.

## 날짜를 바꾸면 지도도 바뀌어야 했어요

학원 담당자는 날짜별 배차와 여러 노선을 보면서 학생의 탑승 상태, 승하차 정류장을 확인하고 변경해야 했어요. 새 화면에는 학원별 배차 조회와 복수 노선 지도, 탑승 상태·정류장 변경, 접근 제한을 연결했습니다. 관제 데이터는 폴링으로 갱신하고 노선과 정류장 관리에는 Kakao Map을 썼어요. 이 운행 화면 변경은 병합됐고, 이후 학생 탑승 일정과 위치의 일괄 등록 기능도 이어졌습니다.

학원·날짜·시간·배차 선택이 서로 다른 대상을 가리키지 않도록 상태를 관리했어요. 학원이 바뀌면 이전 선택을 초기화하고, 날짜가 바뀌면 시간과 경로 선택을 비웠습니다. 탑승 상태나 정류장 변경이 성공한 뒤에는 배차 상세·학생 일정·정류장 목록의 조회 캐시를 무효화해 서버 결과를 다시 가져왔어요. 정류장 드래그에서는 같은 정류장인지, 노선 방향과 출발·도착 제약을 지키는지, 승하차 순서가 뒤집히지 않는지를 확인한 다음 변경 확인으로 이어갔습니다.

정류장 이름을 정확히 모르는 운영자를 위해 주소 검색이나 학원에 연결된 정류장 후보에서 고르는 방식도 제안했어요. 기록된 제안이며 모든 검색 방식이 운영에 적용됐다는 뜻은 아닙니다. 분산된 기능의 운행 화면 재구성과 초기 안정화에 참여했지만, 전체 레거시 이관 완료 시점이나 안정화의 정량 효과는 확인하지 못했어요. 화면과 조회 흐름은 [Yellow Bus 사례](/work/yellow-bus/)에 더 적어 두었습니다.
