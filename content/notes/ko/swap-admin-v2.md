## V2 화면으로 들어왔는데 작업은 V1에 남아 있을 때

2025년 12월 SWAP 운영 Admin에 구독·작업·팩토링 V2 화면과 Fleet API가 들어왔어요. 새 목록을 열 수 있게 돼도 기존 작업 데이터의 조회 경로는 계속 필요했습니다. 특히 기존 작업 상세 주소로 들어온 데이터가 V2 작업이라면 새 상세 화면으로 보내야 했어요.

이 전환에서는 기존 상세의 응답 버전을 확인해 V2 작업을 새 상세로 이동시켰습니다. 이동할 때 `replace`를 써서 전환용 주소가 브라우저 이력에 한 단계 더 쌓이지 않게 했어요. 릴리스 시점에는 작업 상세가 V2를 먼저 조회하고 요청 실패 시 V1을 조회하는 경로도 있었습니다. 모든 실패 원인을 구분해 전환한 것은 아니고, 당시 두 데이터 경로가 공존한 방식이에요.

## 목록은 새 API, 뒤따르는 업무는 기존 API

저는 구독·작업·팩토링의 새 진입 화면과 Fleet API 연동에 참여했어요. 팩토링 목록은 빈 필터를 제외하고 조회하며, 필터가 바뀌면 첫 페이지로 돌아가게 했습니다. Fleet API가 반환한 총 건수와 페이지도 테이블 페이지네이션에 연결했어요. 목록이 새 페이지 응답을 쓰더라도 관련 상세·계약·첨부 업무에는 기존 API 경로가 남아 있었습니다. 팩토링 V2 목록에 Suspense와 ErrorBoundary로 로딩·오류 경계를 둔 팀 릴리스에도 참여했어요.

직원이 화면을 찾아 들어오는 경로도 함께 다뤘습니다. 권한과 사이드바, 결제 조회, 일괄 작업 등 운영 기능의 전환에 참여하며 기존 화면과 V2 화면 사이의 메뉴와 접근 경로를 살폈어요. 저는 2025년 9월부터 SWAP FE Part Lead로 프론트엔드 기술 의사결정과 개발·리뷰를 맡고 있습니다. 이 V2 작업은 팀 릴리스였고, 제 참여 범위는 주요 기능 개발과 기술 검토·코드 리뷰예요.

2025년 12월 릴리스에는 세 V2 화면과 Fleet API 연동이 병합됐습니다. 작업 상세의 V2 우선 조회와 V1 경로도 당시 기록에 남아 있어요. 공존 경로의 운영 오류율은 따로 측정하지 않았고, 남은 기존 API 업무의 전환 완료 시점도 확인된 결과로 적지 않습니다. 이 글의 범위는 운영 Admin의 전환이며, 화면별 경계는 [SWAP Admin V2 사례](/work/swap-admin-v2/)에 정리했습니다.
