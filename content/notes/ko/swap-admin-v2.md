## 화면보다 먼저 바뀌지 않는 데이터

2025년 12월 주요 릴리스에서 SWAP 운영 Admin에 구독·작업·팩토링 V2 화면과 Fleet API가 들어왔어요. 하지만 기존 작업 데이터의 조회 경로는 계속 필요했습니다. 저는 2025년 9월부터 SWAP FE Part Lead로 프론트엔드 기술 의사결정과 개발·리뷰를 맡고 있고, 이 Admin V2 팀 릴리스에서는 주요 기능 개발과 기술 검토·코드 리뷰에 참여했어요. 여기서 다루는 범위는 운영 Admin이며, 서비스 전체의 이전 완료를 의미하지 않습니다.

새 화면의 진입점만 연결하면 기존 주소나 데이터 버전과 충돌할 수 있었어요. 전환 범위에는 기존 작업 상세에서 응답 버전을 확인하고 V2 작업이면 새 상세로 보내는 흐름이 포함됐습니다. 이 이동에는 `replace`를 사용해 전환용 주소가 브라우저 이력에 한 단계 더 쌓이지 않게 했어요. 릴리스 시점 작업 상세에는 V2를 먼저 조회하고 요청이 실패하면 V1을 조회하는 경로도 있었어요. 이는 당시 공존 방식에 대한 설명이지, 모든 실패 원인을 판별해 안전하게 전환했다는 결과는 아닙니다.

## 새 목록과 기존 상세가 만나는 곳

구독·작업·팩토링 새 진입 화면과 Fleet API 연동에 참여했어요. 팩토링 목록에서는 필터와 페이지 상태를 함께 다뤄 빈 필터를 빼고 조회하며, 필터가 바뀌면 첫 페이지로 돌아가도록 했습니다. Fleet API가 돌려준 총 건수와 페이지를 테이블 페이지네이션에 연결했어요. 한편 신규 목록이 Fleet API의 페이지 응답을 사용하더라도 관련 상세·계약·첨부 업무에는 기존 API 경로가 남아 있었습니다. 팩토링 V2 목록에 Suspense와 ErrorBoundary로 로딩·오류 경계를 구성한 팀 릴리스에도 참여했어요.

직원이 실제로 화면을 찾고 접근하는 과정도 전환 대상이었어요. 권한·사이드바, 결제 조회와 일괄 작업 등 관련 운영 기능의 전환에 참여했습니다. 기존 화면과 V2 화면을 연결하는 동안 메뉴와 접근 경로가 업무 흐름에서 빠지지 않도록 살핀 범위예요. V2는 팀이 함께 진행한 릴리스였고, 모든 경로를 혼자 설계하거나 구현했다고 주장할 수는 없습니다.

## 확인된 상태와 남은 질문

2025년 12월 릴리스에는 구독·작업·팩토링 V2 화면과 Fleet API 연동이 병합됐어요. 당시 작업 상세의 V2 우선 조회와 V1 조회 경로도 기록돼 있습니다. 다만 이 공존 경로의 운영 오류율은 별도로 측정하지 않았고, 남아 있는 기존 API 업무가 언제 모두 전환됐는지도 이 사례의 결과로 제시하지 않습니다. 화면과 데이터가 동시에 바뀌지 않는 전환에서 조회와 이동 경로를 함께 챙긴 경험으로 정리할 수 있어요. 구체적인 화면 경계는 [SWAP Admin V2 사례](/work/swap-admin-v2/)에 담았습니다.
