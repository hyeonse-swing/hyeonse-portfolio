## 같은 주문을 보는 두 화면

2026년 바이크 사업에서 첫 주문을 만들고 계약서를 보내는 쪽은 직원이었어요. 사업자는 계약과 미납·납부 내역, 현재 계획을 직접 확인해야 했고요. 차량 인계와 보험 변경까지 이어지는 업무였지만, 새 시스템을 만드는 동안에도 기존 시스템과 수기 작업은 계속됐습니다.

저는 프론트엔드 전반을 맡아 직원용 어드민과 사업자 포털의 진입점을 나눴어요. 기획자의 와이어프레임을 기존 어드민 패턴에 맞춰 화면으로 옮기면서 직원에게는 첫 주문과 계약서 발송을, 사업자 마이페이지에는 상태 조회를 배치했습니다. 2026년 6월 주요 API를 연결했고, 7월에는 사업자가 구독·납부 상태를 확인하고 결제수단 처리 뒤 포털로 돌아오는 흐름을 붙였어요. 기존 데이터 이관과 정합성 보정은 백엔드가 맡았습니다.

## 화면이 API보다 먼저 필요했을 때

반납·인수·보험 변경 API는 화면 작업을 시작할 때 아직 확정되지 않았어요. 비운영 환경의 fixture로 업무 순서와 화면 상태를 확인하면서, 나중에 연결할 API와 필드, 교체할 부분을 문서에 남겼습니다. 실제 요청·응답이 정해진 뒤에는 차량·스토어·보험 화면을 그 구조에 맞춰 연결하고 기존 필드 표현과의 호환도 화면에서 보완했어요. fixture 형태를 그대로 운영 계약으로 옮기지는 않았습니다.

사용자 구분도 예상과 달랐어요. 사업자 전용 모델이 따로 생길 것으로 봤지만, 실제로는 일반 사용자와 모델을 공유하고 구분값을 썼습니다. 사업자는 일반 SWAP 서비스도 이용할 수 있어서 기존 이용 흐름은 유지한 채 사업자 전용 메뉴·페이지·API를 분리했어요. 구분값은 백엔드와 맞추고, 접근 거절 후 안내와 이동은 프론트엔드에서 처리했습니다. 포털 데이터는 인증 상태 복원과 접근 확인을 마친 다음 스토어 목록, 선택한 스토어 상세 순서로 조회했어요.

## B2B 테스트를 통과한 뒤 본 B2C 화면

Playwright E2E는 B2B 응답을 기준으로 통과했어요. 그런데 직접 화면을 보니 B2C 응답에는 사업자 정보 객체 자체가 없어 필요한 정보가 비었습니다. 백엔드에 응답 보완을 요청하고 사용자 유형별 화면 조건을 고친 뒤, 해당 케이스를 다시 정의해 자동화와 직접 확인을 반복했어요.

API 확정 전후의 업무 순서는 각각 확인했어요. 화면과 데이터 흐름은 [바이크 운영 사례](/work/bike-operations/)에 더 자세히 적었어요.
