## 주문을 만드는 사람과 확인하는 사람이 달랐어요

2026년 바이크 사업에서는 첫 주문과 계약서 발송을 직원이 맡고, 사업자는 자신의 계약과 납부 상태를 확인해야 했어요. 차량 인계와 보험 변경도 운영 업무에 걸쳐 있었고, 새 시스템을 만드는 동안 기존 시스템과 수기 업무는 계속됐어요. 저는 프로젝트의 프론트엔드 전반을 맡아 직원용 어드민과 사업자 포털 화면을 만들었습니다. 기존 데이터 이관과 정합성 보정은 백엔드의 책임이었어요.

직원 어드민에서는 첫 주문을 만들고 계약서를 발송하도록 했어요. 사업자 마이페이지에는 계약, 미납·납부 내역, 현재 계획을 조회하는 화면을 뒀습니다. 기획자의 와이어프레임을 기존 어드민 패턴에 맞춰 구체화하면서, 어느 업무가 어느 사용자에게 필요한지 화면의 진입점부터 구분했어요. 2026년 6월 주요 API 연동에 이어 7월에는 사업자가 구독·납부 상태를 보고 결제수단 처리 뒤 돌아오는 포털 흐름을 연결했습니다.

## API가 미정일 때 확인할 수 있었던 것

반납·인수·보험 변경 API가 확정되기 전에 화면 작업이 필요했어요. 비운영 환경의 fixture로 업무 순서와 화면 상태를 먼저 확인하고, 실제 연동에 필요한 API와 필드, 교체할 부분을 문서화했습니다. fixture의 형태를 운영 계약으로 간주하지 않고, 실제 요청·응답이 정해진 뒤 차량·스토어·보험 화면을 그 구조에 맞춰 연결했어요. 기존 필드 표현과의 호환도 화면에서 보완했습니다.

사업자는 별도 사용자 모델을 쓸 것으로 예상했지만, 실제로는 일반 사용자와 공통 모델을 쓰고 구분값으로 나뉘었어요. 사업자도 일반 SWAP 서비스를 이용할 수 있었기 때문에 일반 이용 흐름은 유지하고 사업자 전용 메뉴·페이지·API를 분리했습니다. 백엔드와 구분값을 맞췄고, 접근이 거절된 뒤의 안내와 이동은 프론트엔드에서 처리했어요. 포털 조회는 인증 상태 복원과 접근 확인이 끝난 뒤 스토어 목록, 선택한 스토어의 상세 순서로 진행되도록 했습니다.

## 자동화가 놓친 응답 형태

Playwright E2E가 B2B 응답을 전제로 통과한 뒤 직접 화면을 확인하면서, B2C 응답에는 사업자 정보 객체 자체가 없어 필요한 정보가 비는 경우를 찾았어요. 백엔드에 응답 보완을 요청하고 사용자 유형별 화면 조건을 고쳤습니다. 해당 케이스를 다시 정의한 뒤 자동화와 직접 화면 확인을 모두 반복했어요. 이 과정은 테스트 통과만으로 사용자 유형별 실제 표시를 확인했다고 볼 수 없다는 점을 보여줬습니다.

결과적으로 직원의 첫 주문·계약 발송과 사업자의 상태 조회 흐름을 구현했고, API 확정 전후의 업무 흐름을 각각 확인했어요. 실제 이용률, 수기 작업 감소량, 비용 효과는 별도로 측정하지 않았습니다. 구현 범위와 더 자세한 화면·데이터 흐름은 [바이크 운영 사례](/work/bike-operations/)에 정리돼 있어요.
